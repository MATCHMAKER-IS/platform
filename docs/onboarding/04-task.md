# はじめての1機能(実地課題)

この基盤の目的は**属人化を防ぐこと**。しかし基盤そのものが一人しか触れない状態なら、
目的は達成できていない。それを確かめる唯一の方法は、**別の人に実際に作ってもらうこと**。

この文書は、その最初の課題。**読む人が作業し、教えた人が答え合わせをする。**

---

## この課題のねらい

- 新しく入った人が、**手順書だけで**画面を1つ作れるかを確かめる
- 詰まった箇所は「その人の理解不足」ではなく **基盤側の欠陥** として扱い、直す

> 詰まったら遠慮なく詰まってほしい。**詰まった場所こそが、この課題の成果物**。

## 課題

社内の**会議室予約**を記録する画面を1つ作る。

| 項目 | 内容 |
|---|---|
| 一覧 | 予約中のものを表で表示する |
| 登録 | 「会議室名」「予約者」「利用日」を入力して追加する |
| 取消 | 行ごとに「取消」ボタンを押すと一覧から消える |

**やらないこと**: 認証、DB、権限、デザインの作り込み。データは画面の状態(メモリ)でよい。

> **題材は 2026-08 に「備品貸出」から差し替えた。**
> 備品貸出は `/apps/equipment` と `/lending` に実装があり、**答えがリポジトリの中にあった**。
> 課題として成立していなかったので、実装の無い題材にしてある。
> 逆に、**近い形の見本として `/lending` を読んでよい**（下の「参考にする画面」）。

## 進め方

### 1. 動かす(目安 30 分)

```bash
pnpm install
pnpm doctor
pnpm dev:showcase
```

- `http://localhost:3001` が開けたら成功
- **ここで詰まったら、それ以上進まずに記録する**(環境構築は最も詰まりやすい)

### 2. 参考にする画面を読む(目安 30 分)

このデモサイトで、近いものを探して**コードを読む**。

- `/lending` … 一覧・登録・削除だけの**最小**の画面。今回の課題に一番近い
- `/master` … 同じことを項目定義つきで汎用化したもの（次の段階）
- `/ui` … 使える部品の一覧
- `/faq` … 迷ったときの Q&A

該当ファイル: `apps/showcase/src/app/lending/page.tsx` / `apps/showcase/src/app/master/page.tsx`

### 3. 作る(目安 2〜3 時間)

`apps/showcase/src/app/meeting-room/page.tsx` を新しく作る。

**画面を作るだけでは preflight が通らない。** `docs/ops/NEW_APP.md` の 6 手順
(画面 → nav.ts → overviews.ts → 資料の本数 → 生成物 → 確認)を順にやること。
どれを忘れても検査が具体的に教えてくれるので、覚える必要はない。

守ること(トップページの「開発の流れ」と同じ):

- `<button>` や `<input>` を直接書かず、`@platform/ui` の部品を使う
- `console.log` を使わない
- 失敗しうる処理は `Result` で返す(この課題では出番が無いかもしれない。無くてよい)

### 4. 確認する(目安 30 分)

```bash
node tools/preflight.mjs
```

全部緑になれば完成。赤くなったら、表示されたファイルと行を見て直す。

## 教えた側がやること

課題が終わったら、**上の表を見て基盤を直す**。ここが本番。

| 記録された内容 | 直す場所 |
|---|---|
| 環境構築で詰まった | `docs/onboarding/01-setup.md` / `pnpm doctor` の診断を増やす |
| どの部品を使えばいいか分からなかった | `/ui` デモ・トップページの「開発の流れ」 |
| 作法(Result / logger / env)の理由が分からなかった | `/faq` に Q&A を足す |
| エラーの意味が分からなかった | エラーメッセージ自体を直す(**メッセージは最も読まれるドキュメント**) |
| 手順書のとおりにやったのに動かなかった | 手順書を直す。`node tools/check-docs-links.mjs` で参照切れも確認 |

### 判定

- **手順書だけで完成した** … 基盤は他の人にも使える。次の人は別の課題へ
- **口頭の補足が必要だった** … その補足内容が、そのまま**不足しているドキュメント**
- **完成しなかった** … 基盤側の課題。作った人の問題ではない

#### 第5回(2026-08-09・題材「時刻と帳票」の下調べ)の結果

またしても**下調べだけ**で見つかった。時刻の表示は `ja-JP` で統一されていて健全だったが、
**サーバ側の年月日の解釈**が 9 箇所で TZ 依存だった(会計 8 + 採番 1)。
`check-utc-date` は既にあったが `toISOString()` しか見ておらず、
`getFullYear()` 系は素通りしていた。**検査があることと、その範囲が足りることは別。**

#### 第4回(2026-08-09・題材「社員名簿」の下調べ)の結果

画面を作る前の**下調べだけで**見つかった。氏名の五十音順を実装しようとして
`localeCompare` の使われ方を見たところ、**11 箇所中 10 箇所がロケール未指定**だった。
日本語が入るのは 3 箇所で、いずれも並び順が実行環境で変わる状態。

**作らなくても、作ろうとして基盤を調べるだけで穴は出る。**
「この機能を作るなら基盤の何を使うか」を辿る作業そのものに価値がある。

#### 第3回(2026-08-09・題材「経費申請」)の結果

**手順書だけで完走した。** 見つかったのは**負の金額の表示**——`formatYen` が
`¥-5,000` を返しており、日本の会計帳票の書き方(`△5,000`)になっていなかった。
`packages/accounting` は消費税の還付(マイナス)を扱うので、実際に出る値だった。

**題材を変えると、出てくる穴も変わる。** 会議室予約では日本語入力、
経費申請では金額表記——どちらも**日本語環境でしか起きない**。
次の題材を選ぶときは、まだ触っていない領域(時刻・住所・氏名の並び・帳票の印刷)を狙うとよい。

#### 第2回(2026-08-09)の結果

**手順書だけで完走した。** 第1回で直した 6 件はいずれも再発せず、
`pnpm gen:all` も手順書のとおりに動いた。**手順そのものは実用に耐える。**

ただし**課題の完了条件を満たせなかった**——「キーボードだけで登録から取消まで操作できる」
とあるのに、見本の `/lending` が Enter に対応していなかった。
そこを調べたことで、**日本語入力の変換確定で誤送信する箇所が 21 中 20** 見つかった。
基盤の部品 4 つが含まれており、使う側すべてに伝播していた。

**課題は「新人が作れるか」を測る道具だが、作る過程で基盤の穴が出てくる方が価値が大きい。**
今回の穴は、英語で動作確認すると絶対に気づけない種類のものだった。

#### 第1回(2026-08-08)の結果

**手順書だけで完成した。** ただし上の 6 件で詰まり、うち 4 件は**手順書が実態と
食い違っていた**もの(ADD_DEMO の手順4・手順5、参照先アプリ、smoke のラベル)。
いずれも修正済み。

詰まりの性質に共通点がある: **「以前は正しかったが、実装を直したときに文書と
ラベルだけが取り残された」**。数値は `check-doc-numbers` が見張っているが、
**手順そのもの**(「このファイルのこの文字列を直せ」)は誰も見張っていない。
次にこの種の食い違いを減らすなら、手順書のコマンドだけでなく
**手順書が指す文字列の実在**まで検査する余地がある。
