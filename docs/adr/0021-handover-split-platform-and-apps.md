# 0021: 引き継ぎ資料を基盤とアプリで分ける

- 日付: 2026-08-13 / 状態: 採用

## 文脈（なぜ決める必要があったか）

`docs/ops/HANDOVER.md` が **1,200 行を超え**、
**基盤の判断とアプリ固有の話が混ざっていました**。

- 基盤（`packages/` `tools/`）の落とし穴
- `internal-app` の画面や業務ルール
- `line-console` の LINE 固有の注意

**探すときに全部を読むことになり、実際には誰も読みません。**

さらに、**アプリが増えるたびにこの資料が伸びます**——
**5 個目のアプリを作る人が、1〜4 個目の話を読む**ことになります。

## 決定

**基盤のことは `docs/ops/HANDOVER.md`、アプリのことは `apps/<名前>/HANDOVER.md`** に分ける。

| 内容 | 書く場所 |
|---|---|
| `packages/` `tools/` の落とし穴・判断 | `docs/ops/HANDOVER.md` |
| `apps/showcase` `apps/crud-template` | `docs/ops/HANDOVER.md`（**見本と雛形なので基盤の一部**） |
| 各アプリの画面・業務ルール・設定 | `apps/<名前>/HANDOVER.md` |
| 各アプリの出し先・試験の状況 | `apps/<名前>/README.md`（このアプリの運用） |

**判断の基準**: **他のアプリでも起きるなら基盤側**、
**そのアプリでしか起きないならアプリ側**。

**迷ったら基盤側**——**アプリ側に書いたものは、別のアプリを作る人が読みません**。

## 理由

**`showcase` と `crud-template` を基盤側に入れた理由**:
**他のアプリを作る人が真似する**ものだからです。
「showcase での判断」は、**次のアプリでも同じ判断になります**。

**既存の記述を移さなかった理由**:
**仕分けを誤ると、基盤の知見がアプリ側に埋もれます**。
実際に `apps/internal-app/src` を指す 4 件を調べたところ、
**内容は基盤の知見**でした（「金額の表記がサーバの `LANG` に依存」は `formatYen` の話）。

**パスで機械的に判断すると間違えます。**
2026-08 より前の記述は**そのまま残し**、**探すときは両方を見る**ことにしました。

## 結果

- 各アプリに `HANDOVER.md` を新設（**「どちらに書くか」の表つき**）
- `new-app` が**新しいアプリにも作る**ようにした（検査で見張り）
- `crud-template` にも置き、**触るときの注意**を書いた

## 覆すとしたら

**アプリが 1 つに戻ったとき**は、分ける意味がなくなります。
そのときは**基盤側に統合**してください——ただし
**「どちらに書くか」の判断が要らなくなった**ことを確かめてから。

**逆に、アプリが 10 個を超えたら**、
**アプリ側の HANDOVER も長くなりすぎる**かもしれません。
そのときは**アプリごとに更に分ける**（画面・業務・運用）ことを検討してください。
