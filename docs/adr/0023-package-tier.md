# ADR 0023: パッケージに成熟度（tier）を宣言させる

- 状態: 承認
- 日付: 2026-08-14

## 背景

`packages/` は 119 件まで増えたが、**すべて横並び**だった。`package.json` の形も
README の有無も同じで、外から見て区別が付かない。

2026-08 に実際の利用状況を数えたところ、**実アプリ（`internal-app` /
`public-site` / `line-console` / `crud-template`）から一度も参照されていない
パッケージが 26 件**あった。showcase（基盤のデモ）でしか動いていない。

区別が付かないことで、方向の違う 2 つの問題が同時に起きる。

- **使う側**は、未検証のパッケージを本番アプリで掴む。動かなくても
  「基盤にあったから使った」としか言えない。
- **直す側**は、26 件を**本番品質で保守し続ける**。依存の版上げ、脆弱性対応、
  破壊的変更の回避——**使われていないものにこの労力を払い続ける**。

後者は情シス 1〜2 名の体制では効いてくる。ADR 0011 で「バージョン管理はしない」と
決めているため、**「これは変わるかもしれない」を伝える手段が他に無い**ことも大きい。

## 決定

**すべての基盤パッケージに `package.json` の `platform.tier` を宣言させる。**

| tier | 意味 |
|---|---|
| `stable` | 実アプリが使っている、または stable が依存している。**公開 API を壊す変更には Changesets の major が要る** |
| `incubating` | **実アプリでの使用実績がまだ無い。** showcase での動作確認までは済んでいる。**予告なく変わる** |
| `deprecated` | 廃止予定。新規利用禁止。移行先を README の冒頭に書く |

あわせて **`stable` は `incubating` / `deprecated` に依存できない**ことを
`tools/check-package-tier.mjs` で機械的に守る。「安定」と言いながら、
**足元が動くものの上に立たない**ためである。

初期値は「実アプリから推移的に到達できるか」で機械的に決めた
（stable 93 / incubating 26）。

## 理由

**なぜ削除ではなく tier か。** 26 件は動くし、テストも README もある。
消すと作り直しになる。**「まだ実績が無い」と表示するだけ**なら、
資産は残しつつ保守の優先度だけ下げられる。

**なぜ `package.json` に書くか。** 別ファイルの一覧にすると、
パッケージを足したときに**書き忘れても気づけない**。`package.json` なら
`check-package-tier` が「宣言が無い」で落とせる。

**なぜ依存の向きまで縛るか。** tier が表示だけなら、
`stable` の中身が `incubating` でできていても通ってしまい、
**stable という表示が嘘になる**。実際、導入時に `ui`(stable) が
`print` / `hid` / `device`(incubating) に依存していることを
この検査が検出した——**表示だけなら見逃していた**。

## 影響

- tier を上げるのは**実アプリで使ってから**。「そのうち使う」で上げると
  この区別は意味を失う。
- `incubating` を本番で使いたくなったら、**使ってから上げる**のではなく
  **上げてよいか判断してから使う**。判断の材料は「壊れたとき誰が直すか」。
- 新しいパッケージの既定は `incubating`。`scaffold` もそう出力する。

## 代替案

- **削除する** … 資産を捨てることになる。将来必要になったとき作り直しは高い。
- **README に「試験的」と書く** … 機械が読めない。書き忘れても落ちない。
- **別ディレクトリ（`packages` の下に experimental を切る）へ移す** … import パスが変わり、
  昇格のたびに全参照を書き換えることになる。`.gitignore` で
  workspace から外した `apps/` と同じ問題（検査対象から漏れる）も起きる。
