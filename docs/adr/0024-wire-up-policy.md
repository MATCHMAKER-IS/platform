# ADR 0024: 繋ぎ込みは「アプリ側の CI」と「被覆率の検査」で担保する

- 状態: 承認
- 日付: 2026-08-14

## 背景

この基盤は「部品をどう作るか」を丁寧に決めてきた（ADR 0002 分離 / 0015 分割基準）。
しかし **「作った部品をどう繋ぐか」の決定が無かった。**

決定が無いので検査も生まれない。この基盤の骨格は
「**決めたことを機械に守らせる**」だが、**繋ぎ込みの領域だけ、その骨格が及んでいなかった。**

### 症状①: 基盤の CI がアプリを見られない

ADR 0021 で「アプリは各自のリポジトリで管理する」と決め、
`.gitignore` に `apps/*` を書いた。**この判断自体は正しい。**

ただし副作用がある。基盤の検査 79 種類のうち **50 種類はアプリを走査する**。
そのアプリが基盤のリポジトリに無いのだから、**50 種類は対象がほとんど存在しない**。

2026-08 の実測:

| | 手元 | 基盤の CI |
|---|---|---|
| 見える API | 264 本 | **22 本** |
| 見えない | — | **242 本（92%）** |

`check-api-auth` は手元で「API 264 本 / どちらも無い 0」と緑を出す。
**その緑は、CI では 22 本ぶんの意味しか持たない。**

アプリ側 CI のテンプレートは `apps/crud-template/.github/workflows/ci.yml` に
**存在していた**。しかし実アプリ 3 つ（internal-app / public-site / line-console）に
**1 つも置かれていなかった**——テンプレートはあったが、誰も配っていなかった。

さらにテンプレート自身にも欠陥があった。`pnpm check` を「72 種類」と称して
呼んでいたが、`pnpm check` の実体は `typecheck && lint && smoke` であり、
**smoke が呼ぶのは 16 種類**。アプリを見る検査の大半が素通りしていた。

### 症状②: 「存在する」を「繋がっている」と読み違える

部品を作った人は「あること」を知っているので、**繋ぎ忘れに自分では気づけない。**
気づくのは半年後に別の人が同じものを自作しようとしたとき、
あるいは**事故が起きたとき**である。

`withIdempotency` は基盤にあり、`purchase-orders` で使われていた。
**存在も使用実績もある。** それでも、二重送信で実害が出る API 15 本のうち
**繋がっていたのは 1 本**だった。

実際、この検査を入れた初回に `apps/showcase/src/app/api/media-probe/route.ts` が
**アップロードを拡張子だけで判定してディスクに書き、ffprobe に渡している**のを
検出した。`detectFileType` は基盤にあったのに、繋がれていなかった。

## 決定

**次の 2 つで担保する。**

### 1. アプリ側リポジトリの CI で、基盤の検査を回す

**サブモジュール化はしない。** ADR 0021 の「別チームが別の速さで改修できる」を
壊すことになり、一人〜数人の体制では管理コストも見合わない。

代わりに、アプリの CI が**基盤を隣に clone して `node tools/preflight.mjs` を回す**。
アプリは `workspace:*` で基盤を参照しているので、**どのみち基盤が隣に要る**——
追加の仕組みではなく、既にある依存関係をそのまま使う。

`tools/check-app-ci.mjs` が、全アプリがこのワークフローを持っていること、
テンプレートからずれていないことを見張る。**「テンプレートがある」は
「使われている」ではない**——今回の教訓をそのまま機械化した。

### 2. 安全に関わる部品は「被覆率」で見る

`tools/check-safety-parts.mjs` に、部品ごとの
**分母（使うべき場所）と分子（実際に使っている場所）**を定義する。

**「1 箇所でも使われていれば緑」にしない。** それでは 12 本中 1 本だけ
認可を通している状態が緑になる。実際に `withIdempotency` は
「使われている」のに 1/15 だった。

- `critical: true` の部品（無害化・種別判定・宛先の検証・鍵の比較）は **100% を要求**。
  レート制限・監査ログ・冪等は下限ラチェット（一度に全部へ付けるのは現実的でない）。
  繋ぎ忘れがそのまま事故になるので、ラチェットで待てない。
- それ以外は**下限ラチェット**。いきなり 100% を課すと CI が止まり、
  **止まった CI は無効化されて何も守らなくなる**（`check-maintainability` と同じ理由）。

正当な例外は、**その場に理由つきの宣言を書く**。
`check-api-auth` の `// public-api:` と同じ作法である。

| 宣言 | 何を免除するか |
|---|---|
| `// safe-source: <理由>` | その入力は信頼できる（基盤が組み立てた HTML など） |
| `// no-rate-limit: <理由>` | レート制限（死活監視は数十秒ごとに叩かれるのが要件） |
| `// no-audit: <理由>` | 削除の監査記録（一時データ・下書き・キャッシュ） |
| `// no-ssrf-check: <理由>` | 送信先の検証（環境変数由来の固定 URL） |

**印は部品ごとに分ける。** 1 つの印で全部が黙ると、
**レート制限を免除した API が監査ログまで免除される**。

### 3. 検査が正しく測っているかを、導入時に必ず目視する

**これが今回いちばん時間を要した部分である。** 見張り対象を 7 部品に増やす過程で、
**検査自身の誤りが 3 件**見つかった。

| 誤り | 何が起きていたか |
|---|---|
| ラッパー名を拾えていない | `internal-app` は `server/rate-limit.ts` に `getLoginLimiter` を置いており、**基盤の関数名が route に現れない**。ログイン API を「未接続」と誤検出していた |
| **探す関数が違った** | SSRF の守りは `isSafeExternalUrl` なのに `isPrivateIp` を探していた。「1 箇所で使用中」の実体は **showcase の解説ページ**で、**正しく守っている `webhook-emit` は数えていなかった**——両方向に誤っていた |
| 正当な例外を拾っていた | `/api/health` は数十秒ごとに叩かれるのが要件。制限すると**監視そのものが落ちる** |

**「部品はあるのに使われていない」と同じことが、検査にも起きる。**
置いただけでは意味がなく、**測っている対象が実態と合っているか**を
確かめて初めて機能する。`--list` で一件ずつ目視できる形にしてあるので、
**下限を刻む前に必ず中身を見ること。**

---

## 理由

**なぜツールの除外リストではなく、その場の宣言か。**
除外正規表現を伸ばすと基盤全体に効いてしまい、**次に本物の穴が空いたときも黙る**。
宣言はその場に残るので、**読んだ人がその場で妥当性を判断できる**。

**なぜ登録する部品を絞るか。**
判断基準は「**繋ぎ忘れると、そのまま事故になるか**」。
便利なだけの部品を登録すると、使う必要のない場面で赤くなり、
**そのうち誰も見なくなる**。検査そのものが形骸化する。

**未使用がすべて悪いわけではない。** 「SSO なら IdP に任せる」と決めた結果として
使われない部品は、**使わないのが正解**である。
区別すべきは「**使わないと危ないのに未使用**」かどうか。

## 影響

- **新しいアプリは、作った直後に CI を置くこと。** `pnpm new-app` がコピーするが、
  `repository: <あなたの組織>/platform` の書き換えは手作業。
- 基盤側で `preflight` を重くすると、全アプリの CI が遅くなる。
  **検査を足すときは実行時間も見ること。**

  実測（2026-08）で全 79 種類は **約 6 分**、うち `verify-checks` だけで
  **174 秒**を占めていた。これは「検査自体が発火するか」を確かめるもので、
  **アプリのソースを 1 行も見ない**。

  そこで `node tools/preflight.mjs --apps-only` を用意した。
  **基盤そのものの健全性を見る 22 件を飛ばし、約 2 分 40 秒**になる
  （アプリ側 CI のテンプレートはこちらを使う）。飛ばす一覧は
  `tools/preflight.mjs` の `PLATFORM_ONLY`。

  **アプリを走査する検査をここへ入れないこと。** 入れた瞬間、
  そのアプリは**誰にも検査されなくなる**——基盤の CI からは
  アプリのソースが見えないためで、この ADR が解こうとした問題そのものに戻る。
- `check-safety-parts` の分母は**業務判断で調整する**。冪等が要る API の範囲は
  基盤が決められない。語の並びを変えれば下限ラチェットが自動で追随する。

## 却下した案

- **サブモジュール化**（基盤の git からアプリが見える）… 一元管理できるが、
  ADR 0021 を実質的に覆す。アプリの改修のたびに基盤側の更新が要る。
- **検査ツールを npm へ公開して配る** … ADR 0011 で「公開しない」と決めている。
  内製で数人が触るだけなら、公開の手間より clone の方が確実。
- **可視化のみ（レポートを出すだけ）** … 見られなくなる。
  実際 `advisor` は繋ぎ忘れを 1 件も検出できていなかった。
