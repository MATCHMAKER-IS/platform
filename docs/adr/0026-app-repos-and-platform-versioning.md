# ADR 0026: アプリを別リポジトリにし、基盤に版を振る（ADR-0011 を置き換える）

- 日付: 2026-08-18 / 状態: **採用**（レジストリは GitHub Packages / スコープは `@mtmk-cc`）
- 置き換える: [ADR-0011](0011-no-versioning-monorepo.md)

## 文脈(なぜ決める必要があったか)

`ADR-0011` は「基盤パッケージにバージョンを振らない」と決めました。
その理由は明確でした——

> **単一リポジトリ・単一デプロイ単位**である。基盤とアプリが常に同時に
> デプロイされるため、「アプリ A は基盤 v1.2、アプリ B は v1.5」という状態が発生しない。

**この前提が崩れます。**

2026-08 の方針で、次のことが決まりました。

- **アプリは数十本になる**（いまは 3 本）
- **アプリは別リポジトリで管理する**（基盤のソースはアプリ側に持たない）
- **基盤の更新は月 2 回程度**
- **アプリ側から「いまどの版か」を見て、更新できるようにしたい**

別々に更新される以上、「アプリ A は 8 月版、アプリ B は 10 月版」は**普通に起きます**。
`workspace:*`（同じリポジトリのソースを直接見る）は使えません。

## 決定

**(1) リポジトリを分けます。**

```
platform/            ← 基盤（packages / tools / docs）
  apps/
    showcase/        ← 残す。**部品の見本は基盤の一部**
    crud-template/   ← 残す。`pnpm new-app` のコピー元
app-internal/        ← 出す（680 ファイル）
app-line-console/    ← 出す
app-public-site/     ← 出す
app-xxx/             ← 今後、数十本
```

`showcase` と `crud-template` を残すのは、**基盤と一緒に動かないと意味が無い**からです
——部品を直したら見本も直る必要があり、雛形が古いと生成したアプリが最初から古くなります。
実際 `gen-portal-extras.mjs` と `new-app.mjs` がこの 2 つを参照しています。

**(2) 版は日付式・120 パッケージ一括（lockstep）にします。**

`2026.8.0`（年.月.パッチ）。**個別に振りません**——120 個の組み合わせを検証するのは
現実的でなく、「`ui` は 3.1 で `form` は 2.8」という状態を人が追えません。

**(3) アプリは範囲指定で参照します。**

```json
{ "dependencies": { "@mtmk-cc/ui": "^2026.8.0" } }
```

ご要望の「アプリ側から版を見て更新」は、**pnpm 標準の `outdated` / `update`**で実現します。独自のツールを作りません。

## レジストリ: GitHub Packages（2026-08-18 決定）

CodeArtifact は使わない方針のため、選択肢は 2 つでした。**案 A を採ります。**

**決め手**: サーバを 1 台増やして運用し続けるより、**改名は一度きり**で済むこと。
GitHub は既に使っているので、権限も既存の仕組みに乗ります。

### 採用：案 A（GitHub Packages + スコープ改名）

GitHub Packages の npm レジストリは、**スコープがリポジトリの所有者と一致していなければなりません**
（`@my-org/test` は `my-org/test` に publish される）。
つまり `@platform/*` を使い続けるには、**`platform` という名前の GitHub Organization**が要ります。

現実的には**自社の Organization 名へ改名**することになります。

**改名するのは「パッケージ名の接頭辞（スコープ）」だけ**です——
ローカルのフォルダ名（`platform/`）も、GitHub のリポジトリ名も、
`packages/` の構成も**変わりません**。

**注意: GitHub の Organization 名にドット（`.`）は使えません。**
ドメイン名（例 `mtmk.cc`）はそのままスコープにできないので、
**GitHub 上の実際の Organization 名**（`https://github.com/【ここ】/platform`）に
合わせてください。

- `@platform/ui` → `@自社名/ui`
- **影響: 1,597 ファイル / 8,673 箇所**（機械的な置換で済みますが、後戻りは大変です）
- 費用は GitHub の既存契約の範囲（別途の利用料が要るかは要確認）

### 見送り：案 B（Verdaccio を社内に立てる）

スコープの制約がないので、**`@platform/*` のまま**使えます。

- 改名が不要（8,673 箇所を触らない）
- **サーバの用意と運用**が増える（EC2 / ECS / 社内サーバ）
- バックアップ・可用性を自分たちで見ることになる

### 比べどころ

| | 案 A（GitHub Packages） | 案 B（Verdaccio） |
|---|---|---|
| 改名 | **必要**（8,673 箇所） | 不要 |
| 運用するもの | 無し（GitHub 任せ） | **サーバ 1 台** |
| 権限管理 | GitHub のまま | 自分たちで設定 |
| 止まったとき | GitHub 次第 | **自分たちで直せる** |

**改名は一度きり、サーバの運用は続きます。** この理由で案 A を選びました。

**スコープは `@mtmk-cc`**（GitHub Organization 名。ドットは使えないため `mtmk.cc` ではない）。

```
@platform/ui  →  @mtmk-cc/ui
```

## 検討した代替案と見送り理由

**(a) Git タグ + 取り込みスクリプト（`platform-sync.mjs` の拡張）**
アプリが 2〜3 本なら十分でしたが、**数十本では「どのアプリがどの版か」を人が管理する**
ことになり破綻します。依存の解決も自前になります。見送り。

**(b) git submodule**
仕組みは簡単ですが、**扱いを間違えやすい**（更新し忘れ・detached HEAD）。
非エンジニアが触る前提と噛み合いません。見送り。

**(c) 1 パッケージに束ねて配布（`@org/platform` 一本）**
publish は 1 つで済みますが、**アプリが使わない部品まで全部入ります**。
サブパスで切れるとはいえ、依存の見通しが悪くなるため見送り。

## 影響(良い点・受け入れるコスト)

**良い点**
- **基盤の更新をアプリ側が選べます**（いまは基盤を直した瞬間に全アプリへ影響）。
  月 2 回という更新頻度を、実際に制御できるようになります。
- **基盤リポジトリが軽くなります**。`internal-app` だけで 680 ファイルあり、
  いま preflight が 5〜10 分かかる一因です。
- 権限を分けられます（A 事業部のアプリを B 事業部が触れない）。

**受け入れるコスト**
- **`ADR-0011` の利点を失います**。基盤を直しても、アプリ側が pnpm の `update` するまで
  反映されません。**「直したのに直っていない」という混乱**が必ず起きるので、
  更新手順を `docs/ops/` に置く必要があります。
- **破壊的変更の検出（`api-surface.mjs`）が効く範囲が狭まります**。
  いまは「消した API を誰が使っているか」まで分かりますが、
  アプリが別リポジトリになると**基盤側からは見えません**。
  版を上げたアプリ側の CI で気づく形になります。
- 移行そのもの（レジストリの用意・アプリの切り出し・改名の可能性）。

## 進め方（段階的にできます）

1. **レジストリを決める**（案 A / 案 B）← いまここ
2. publish の仕組みを作る（タグ → 一括 publish）。**この時点ではまだ誰も使いません**
3. **アプリを 1 本だけ**切り出して試す（`line-console` が小さくて手頃。24 ファイル）
   → 手順は [docs/ops/APP_EXTRACTION.md](../ops/APP_EXTRACTION.md)
4. 問題が無ければ残りを移す
5. `ADR-0011` を「置換済み」にする

**2 まではいつでも戻せます。** 3 から先が本番です。
