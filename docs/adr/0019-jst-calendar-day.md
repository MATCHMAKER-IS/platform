# 0019: 暦日の比較は JST 基準で行う

- 日付: 2026-07-29 / 状態: 採用

## 文脈(なぜ決める必要があったか)

`@platform/datetime` は「JST 前提の日時ユーティリティ」として作ったが、暦日の比較は
`dayNumber()`(= `getTime() / 86400000`)、つまり **UTC の暦日**で行っていた。

日付だけの値を UTC 0 時の `Date` で表す規約(`utcDate()`)の中では、これで一貫していた。
壊れるのは **「今」を「今日」に変換する境目**だけである。JST は UTC+9 なので、
**日付が変わってから朝 9 時までの 9 時間**、UTC ではまだ前日になる。

実測(JST 2026-07-29 00:30 の時点):

| 呼び出し | 修正前 | あるべき値 |
|---|---|---|
| `isToday(今日)` | `false` | `true` |
| `daysUntil(今日が期限)` | `1` | `0` |
| `isSameDay(08:00 JST, 10:00 JST)` | `false` | `true` |
| `new Date().toISOString().slice(0,10)` | `"2026-07-28"` | `"2026-07-29"` |

さらに `isToday` / `daysUntil` は **既定引数が `new Date()`** だった。呼ぶ側が何も
間違えていなくても、1 日のうち 9 時間だけ答えが変わる。

この不具合は **昼間に書いて昼間に試すと必ず通る**。夜間バッチ・早朝の打刻・締め処理で
初めて出て、しかも「たまにおかしい」としか見えない。テストにも残らない。

`TZ=Asia/Tokyo` を設定しても直らない。`getTime()` と `toISOString()` は
タイムゾーン設定の影響を受けないため。

## 決定

**暦日の比較は JST 基準で行う。**

- `dayNumberJst(date)` を追加し、暦日を扱う関数(`isSameDay` / `isBeforeDay` /
  `isAfterDay` / `daysBetween` / `daysUntil` / `isToday` / `dayOfWeek` /
  `isHoliday` / `holidayName`)をこれに載せ替える
- 「今」から日付を得る口として `todayJst(now?)` と `formatDateJst(date?)` を用意する
- `dayNumber` は UTC の暦日として**そのまま残す**(既存の意味を変えない)
- `new Date().toISOString().slice(0,10)` は `node tools/check-utc-date.mjs` で検出する

**日付だけの値(UTC 0 時)に対しては `dayNumberJst` と `dayNumber` は同じ値になる**
(0 時 + 9 時間は同じ日に収まるため)。祝日表・営業日計算・和暦は日付だけの値で動くので、
載せ替えても結果は変わらない(smoke 1,442 件で確認)。

時刻を含む前後比較(`isPast` / `isFuture`)はインスタント比較(`getTime()`)のままでよい。
これはタイムゾーンに依存しない。

## 検討した代替案と見送り理由

**`dayNumber` 自体を JST 基準にする** — 呼ぶ側が何も考えなくてよくなるが、
「1970-01-01 からの日数」という公開済みの意味が変わる。外部に配る日が来たとき、
同じ名前で違う値を返すことになるので見送った。

**`TZ=Asia/Tokyo` を実行環境に設定する** — `getTime()` も `toISOString()` も
タイムゾーン設定を見ないため、そもそも直らない。環境変数で直ると誤解すると、
「本番だけ直っているはず」という危険な思い込みが残る。

**報告だけして直さない** — 気づけない壊れ方なので、困ってからでは原因にたどり着けない。

## 影響(良い点・受け入れるコスト・関連ドキュメント)

**良い点**: 「今」をそのまま渡してよくなった。呼ぶ側が UTC/JST を意識する必要がない。

**受け入れるコスト**: 暦日比較の結果が変わる場面がある。
`2024-05-01T23:00:00Z` は **JST では 5/2** なので、UTC 基準を前提にしていた既存テスト
1 件を更新した(`calendar.test.ts` の `sameDay/today`)。日本の業務アプリとしては
新しい答えが正しいが、**UTC 基準の値を保存している外部連携がある場合は要確認**。

**移行結果**: `new Date().toISOString().slice(0,10)` は **12 箇所すべてを移行済み**
(`tools/utc-date-limit.json` の上限は 0。**新規に書くと preflight が落ちる**)。
影響が大きかったのは次の 4 件:

| 箇所 | 何がずれていたか |
|---|---|
| 入金記録(`api/invoices/[number]/receipt`) | 入金日。**直後に締め月を判定**するため、月初深夜の入金が前月扱いになる |
| 源泉徴収(`api/withholding`) | 支払日。納付期限(翌月 10 日)の起点 |
| 経費の仕訳(`lib/expense-blueprint`) | 起票日。月初深夜の承認が前月の仕訳になる |
| タスク一覧(`app/tasks`) | 期限切れ判定。深夜〜朝 9 時は**昨日期限が期限切れにならない** |

- 実装: `packages/datetime/src/calendar.ts`
- 検査: `tools/check-utc-date.mjs`(CHECKS.md)
- テスト: `packages/datetime/src/calendar.test.ts`「JST の暦日(9 時間ずれ対策)」

## 追記(2026-08): 月にも同じ問題があった

`check-utc-date.mjs` は**日(`slice(0, 10)`)だけ**を見ており、
**月(`slice(0, 7)`)は素通り**していた。

```ts
new Date().toISOString().slice(0, 7)   // UTC の年月
```

これが 9 画面で使われていた。月初の 00:00〜08:59 に開くと**前月**になり、
勤怠・給与・予算・部署・月次締めがそのままずれる。
とくに月次締めは「前月を締めようとする」ので実害が大きい。

- `formatMonthJst(date?)` を追加した(`formatDateJst` の月版)
- `check-utc-date.mjs` の検出対象に `slice(0, 7)` を足した

**検査があっても、対象が狭ければ通り抜ける。**
「検査があるから大丈夫」ではなく、何を見ているかを確かめる。

## 現況(2026-08 追記)

**検査に穴がありました。** `check-utc-date` は「**今**から UTC の日付を切り出す」
(`new Date().toISOString().slice(0, 10)`)だけを見ており、
**保存済みの ISO 文字列を切る**形(`row.updatedAt.slice(0, 10)`)は素通りしていました。

画面 8 箇所がこの形で、**JST の 00:00〜08:59 に前日が表示**されていました
——とくに `bookings` は**予約できる日の一覧**を作っており、
**今日を選べず既に過ぎた日が並ぶ**状態でした。

すべて `formatDateJst` に直し、**smoke で固定**してあります
(画面で `.slice(0, 10)` を使っていないこと)。
**サーバ側で `+ 9 時間` してから切るのは正しい**ので対象外です。
