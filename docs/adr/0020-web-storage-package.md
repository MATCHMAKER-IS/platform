# 0020: ブラウザの保存(localStorage / sessionStorage)を独立パッケージにする

- 日付: 2026-08-04 / 状態: 採用

## 文脈(なぜ決める必要があったか)

`localStorage` / `sessionStorage` を **28 ファイルが個別に**扱っていた
(`@platform/ui` のテーマ・スキン・言語・レイアウト・列設定、`@platform/form` の下書き自動保存、
デモ各種、アプリのビーコン)。

そのどれもが同じ 4 つを自前で処理しており、**場所ごとに抜けが違っていた**。

1. サーバ側に存在しない(`typeof localStorage === "undefined"` の守り)
2. 書き込みが例外を投げる(プライベートモード・容量超過)
3. 保存済み JSON が古い形のことがある(`as T` で信じている箇所があった)
4. 同じオリジンでの鍵の衝突(接頭辞を付けている箇所と、付けていない箇所が混在)

「同じものを何度も作らない」という基盤の目的にそのまま反する状態だったため、置き場を決める。

## 決定

**新パッケージ `@platform/web-storage` を作る**(localStorage / sessionStorage の
W3C 仕様名「Web Storage」から)。

読み取りは例外を投げず既定値を返し、書き込みは `Result` を返す。
鍵には接頭辞と版を自動で付け、形の検証(`validate`)・TTL・他タブ同期(`subscribe`)を持つ。

## 検討した代替案と見送り理由

| 案 | 見送り理由 |
|---|---|
| **`@platform/storage` に足す** | **`createLocalStorage` が既に「ローカルディスク」の意味で使われている**。ここに localStorage を足すと同名別物になり、ADR-0015 の「同じ機能に別名を付けない/名前で重複に気づけなくする」に正面から反する。加えて `storage` は `node:fs` と S3 SDK を引き込むサーバ側の部品で、扱う物(バイト列 vs 小さな JSON)も保証(サーバで永続 vs 端末ごと・5MB・同期 API)も別 |
| `@platform/storage/browser` のサブパスにする | 上と同じ名前の問題が残る。サブパスは「同じ関心事の依存だけを分ける」ための道具で、関心事が違うものを入れる場所ではない |
| `@platform/cache` に足す | キャッシュは**捨ててよいもの**。利用者の設定は捨ててはいけない。同じ場所に置くと、TTL で消える前提のコードと消えない前提のコードが混ざる |
| `@platform/ui` に置く | UI 以外(フォームの下書き・解析ビーコン)からも使う。UI 依存を引き込ませたくない |
| 何もしない(各所で書き続ける) | 現に抜けが場所ごとに違っていた。増えるほど揃わなくなる |

ADR-0015 の基準 1(依存の重さが違う)に該当する。**ブラウザ専用・依存は core のみ**で、
`@platform/storage` とは依存も関心事も別物のため、既存パッケージへの追加ではなく分離とした。

## 影響(良い点・受け入れるコスト)

良い点:

- 保存の作法が 1 か所になり、抜けが場所ごとに違う状態が解消できる
- 「古い形のデータが端末に残る」事故を `validate` で構造的に防げる
- 他タブ同期・TTL・接頭辞といった、各所では省かれていた機能が既定で付く

受け入れるコスト:

- パッケージが 1 つ増える(113 → 114)
- **残り 27 ファイルの移行が残る**。ADR-0015 の「1 バッチ 1 テーマ」に従い、
  まず `@platform/ui` の `createLocalStorageLayoutStore` のみ移行した
