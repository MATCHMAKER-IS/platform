# 動いているデータを直す（移行手順）

**100 人が使っているものは、止めずに直す必要があります。**

「メンテナンスのため 2 時間停止します」は、
**数人なら通りますが、100 人だと業務が止まります**。

---

## 大原則

### 1. 一度に 2 つのことをしない

**「列を追加して、同時にコードを変える」は失敗します。**

古いコードが動いている間に新しい列ができると、
**古いコードが知らない列に `NOT NULL` があれば書き込みが失敗**します。

**必ず分けてください。**

### 2. 古いコードと新しいコードが同時に動く前提で考える

デプロイの間、**両方が動いています**。
**片方だけが正しく動く変更は、必ずどこかで壊れます。**

### 3. 消すのは最後

**追加は安全、削除は危険**です。
「使っていないはず」の列を消したら、**月次処理だけが使っていた**——
これは実際に起きます。

**1 か月は残してください。**

---

## 列を追加する

**3 回に分けます。**

### 回 1: 列を足す（`NULL` を許す）

```prisma
model ExpenseRow {
  // **必ず `?` を付ける。** `NOT NULL` にすると、
  // **古いコードの書き込みが全部失敗**します。
  memo String?
}
```

```bash
pnpm db migrate dev --name add-expense-memo
```

**この時点で古いコードは何も知りませんが、動き続けます。**

### 回 2: 書き込みと読み込みを足す

コードを更新してデプロイします。
**新しいコードは書き、古いコードは無視する**——どちらも動きます。

### 回 3: 必須にする（必要なら）

**既存の行が全部埋まってから**にしてください。

```sql
-- 埋まっていない行を確認
SELECT COUNT(*) FROM "ExpenseRow" WHERE "memo" IS NULL;
```

**0 件になってから**、`NOT NULL` にします。

---

## 列の名前を変える

**「名前を変える」を 1 回でやってはいけません。**

**5 回に分けます。**

1. **新しい列を足す**（`NULL` 可）
2. **両方に書く**ようにコードを変える（読むのは古い方）
3. **既存の行をコピーする**（下記のバッチ）
4. **読むのを新しい方に変える**
5. **古い列を消す**（**1 か月後**）

**面倒に見えますが、これが一番速い**です。
一気にやって壊れると、**復旧に何倍もかかります**。

---

## 大量のデータを直す

**`UPDATE` を 1 回で流さないでください。**

```sql
-- 危ない: 3 万件を 1 回で更新
UPDATE "ExpenseRow" SET "memo" = '' WHERE "memo" IS NULL;
```

**表全体がロックされ、その間すべての書き込みが止まります。**

**分けて流してください。**

```sql
-- 1,000 件ずつ
UPDATE "ExpenseRow" SET "memo" = ''
WHERE "id" IN (
  SELECT "id" FROM "ExpenseRow" WHERE "memo" IS NULL LIMIT 1000
);
```

**繰り返して、0 件になるまで**流します。
**間に数秒空けてください**——連続で流すと、結局同じことになります。

## 列の型を変える（金額を `Float` → `Int` にする）

**2026-08 に実施した実例**です。同じ形の移行はこの手順でやってください。

### なぜやったか

請求書の `subtotal` / `tax` / `total` / `paidAmount` が **`Float`** でした。
`Float` は二進小数なので `0.1` を正確に表せません。1 件では見えませんが、
**明細を合計し、税を掛け、月次で足し込む**と誤差が積もり、
**請求書の合計が 1 円合わない**という形で表に出ます。

会計では「合わない」こと自体が問題で、原因特定に何時間もかかり、
**監査でも説明できません**。

### 順序が大事（入口 → データ → 型）

**型を先に変えてはいけません。** 小数を送ってくる経路が残っていると、
変えた直後から書き込みが失敗します。

| 順 | やること | なぜ |
|---|---|---|
| **1** | **入口を締める** | 入金 API が `typeof amount === "number"` しか見ておらず、**`1000.5` がそのまま通っていた**。`Number.isSafeInteger` に変えた（NaN / Infinity / 小数をまとめて弾ける） |
| **2** | **既存データを確かめる** | `scripts/migrate-money-to-int.sql` の «STEP 1»。**小数を持つ行が 0 件でなければ進まない** |
| **3** | **バックアップ** | [BACKUP_RESTORE.md](BACKUP_RESTORE.md) |
| **4** | **SQL で変換** | `psql -h localhost -U app -d app -f scripts/migrate-money-to-int.sql` |
| **5** | **schema.prisma を `Int` に** | ここまで来て初めて変える |
| **6** | **`pnpm db push`** | schema と DB が一致しているので、**何も変更しないはず** |
| **7** | **`node tools/check-schema-types.mjs --set-limit`** | 上限を下げて、戻らないようにする |

### なぜ `db push` に任せないか

`db push` は `double precision → integer` を「データ損失の可能性あり」とみなし、
`--accept-data-loss` を要求します。**それで通すと、何がどう丸められたか記録が残りません。**

SQL で明示的に `round()` すれば、**丸め方をこちらが決められます**。

**四捨五入にしてください。** 切り捨てにすると、端数のある入金が
「1 円足りない」扱いになり、**未収として残り続けます**。

### 小数に意味がある列は変えない

**すべての `Float` が誤りではありません。** 次の 2 つは残しています。

| 列 | 理由 |
|---|---|
| `StockMovementRow.unitCost` | 在庫評価は**移動平均法**（`value / qty` の繰り返し）なので、**平均単価に必ず端数が出ます**。`Int` にすると出庫のたびに丸めることになり、**帳簿の在庫金額が実際とずれていきます** |
| `FeePaymentRow.base` | 手数料の基準額。小数に意味がありうる |

**判断の分かれ目は「1 円単位で確定する金額か」です。**

| | 型 | 例 |
|---|---|---|
| 1 円単位で確定する | `Int` | 請求・入金・給与 |
| **計算の途中で使う単価** | `Float` | 在庫の平均単価（**表示するときに丸める**） |

### `WageRow.hourlyWage` は 2026-08 に判断を変えました

以前は「時給。小数がありうる」として残していましたが、**`Int` にしました**。

- 時給は**円単位で決まる**もので、端数のある時給を運用していない
- 一方、毎月の計算で誤差が積み上がると **明細の内訳と合計が 1 円合わない** 形で表に出る
  （説明もできない問い合わせになります）
- 入口（`api/payroll/wage`）も `Number.isInteger` で絞りました

**既存データがあるなら、上の順序どおりに移行してください。**
`scripts/migrate-money-to-int.sql` に、STEP 1 の事前確認と STEP 2 の変換を追加してあります。

> **STEP 1 が 0 件でなければ進まないこと。**
> 丸めると**その人の給与が変わります**。人事の合意なしに実行しないでください。

小数が要るなら **`Decimal @db.Decimal(p, s)`**（PostgreSQL の `numeric`）を使ってください。
`numeric` は 10 進で正確なので、`Float` の問題は起きません。

### 検査で戻らないようにする

`node tools/check-schema-types.mjs` が上限方式で見張ります（`--list` で該当箇所）。

**検出は名前で判断しています。** `FeePaymentRow.base` は
「金額なのに名前に金額語が無く」初回は見逃していました——
**金額を表す語は業務ごとに違う**ので、見つけたら `MONEY_WORDS` に足してください。

## 索引を足す

**`CREATE INDEX` は表をロックします。**

```sql
-- 危ない: その間、書き込みが止まる
CREATE INDEX "idx_expense_status" ON "ExpenseRow" ("status");

-- 安全: 止めずに作る
CREATE INDEX CONCURRENTLY "idx_expense_status" ON "ExpenseRow" ("status");
```

**`CONCURRENTLY` は時間がかかりますが、業務が止まりません。**

**注意**: `CONCURRENTLY` は**トランザクションの中では使えません**。
Prisma のマイグレーションでは、**手で書く**必要があります。

**失敗すると「無効な索引」が残ります**——
`\d` で確認して、残っていたら消してから作り直してください。

## 戻せるようにしておく

### やる前に

```bash
# バックアップを取る（手順は docs/ops/BACKUP_RESTORE.md）
docker compose exec db pg_dump -U postgres app > backup-$(date +%Y%m%d).sql
```

**バックアップ専用の一発コマンドはありません**（手順は `BACKUP_RESTORE.md`）。
**作るなら、まず `pnpm drill`（復元訓練）を通してから**にしてください
——**戻せないバックアップを自動化しても意味がありません**。

**「戻せる」と「戻したことがある」は別**です。
**`pnpm drill`（復元訓練）を一度も走らせていないなら、
バックアップは「あるつもり」**でしかありません。

### 戻し方を先に書く

**変更する前に、戻す手順を書いてください。**

```
戻す手順:
1. アプリを 1 つ前の版に戻す（docker compose のタグを変える）
2. 列は消さない（残っていても古いコードは無視する）
3. 書き込んだデータは…（← ここを先に考える）
```

**3 番目が書けないなら、その変更はまだ早い**です。

## いつやるか

| 変更 | いつ |
|---|---|
| 列の追加（`NULL` 可） | **いつでも**（影響がありません） |
| 大量の `UPDATE` | **業務時間外**（分けて流しても負荷はかかります） |
| 索引の作成 | `CONCURRENTLY` なら**いつでも** |
| 列の削除 | **業務時間外 + 直後に人が見られる時間** |

**金曜の夕方はやめてください。**
**壊れたときに、月曜まで誰も気づけません。**

---

## 記録すること

**何を、なぜ、どう変えたか**を `HANDOVER.md` に書いてください。

とくに**「なぜ 3 回に分けたか」**を書いてください——
次の人が「1 回でいいのでは」と思って、**同じ失敗をします**。
