# 秘密の入れ替え（ローテーション）

**「何分で入れ替えられるか」が被害を決めます。**

鍵が漏れたと分かってから手順を考えると、その間ずっと漏れたままです。
**平時にしか作れない手順**なので、ここに置いています。

## 先に結論

| 鍵 | 入れ替えると何が起きるか | 待ち時間 |
|---|---|---|
| `SESSION_SECRET` | **全員が即ログアウト**（対策あり。下記） | 対策すれば 0 |
| `SECRET_MASTER_KEY` | **保存済みの秘密が読めなくなる**（要移行） | 移行が要る |
| `PREVIEW_TOKEN` / `INQUIRY_TOKEN` | 公開サイト側と**両方**替えるまで機能停止 | 数分 |
| 外部 SaaS の鍵（Zoho / Stripe 等） | その連携だけ止まる | 数分 |
| `POSTGRES_PASSWORD` | **アプリが DB につながらない** | 再起動が要る |

## 漏れたときは、待たない

**このページの「気づかせない入れ替え」は、平時の話です。**

鍵が漏れた疑いがあるときに旧鍵を残すのは、
**漏れた鍵を使い続ける**ことです。その場合は移行期間を置かず、
**全員ログアウトを受け入れて即座に入れ替えて**ください。

告知の文面は用意しておくとよいです（「セキュリティ対応のため再ログインをお願いします」）。

---

## SESSION_SECRET（全員ログアウトさせずに替える）

**そのまま替えると、既に配ってあるクッキーが全部読めなくなります。**
業務時間中にやると問い合わせが殺到し、結果として
**「漏れたので今すぐ替える」ができなくなります**。

`SESSION_SECRET_PREVIOUS` に旧鍵を入れておくと、
**読むときだけ旧鍵も試します**。発行は常に新しい鍵なので、
**利用者が 1 回操作するたびに新しい鍵へ移ります**。

### 手順

**1. 新しい鍵を作る**

```bash
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

**2. 旧鍵を退避してから入れ替える**

```bash
# .env（サーバ上）
SESSION_SECRET=<新しい値>
SESSION_SECRET_PREVIOUS=<いままでの値>
```

```bash
docker compose -f docker-compose.prod.yml up -d app
```

**この時点で誰もログアウトしません。**

**3. 有効期間より長く待つ**

既定は **7 日**です（`maxAgeSec`）。
**この待ち時間を飛ばさないでください**——次の手順で消した瞬間に、
まだ旧鍵のままの人がログアウトします。

**4. 旧鍵を消す**

```bash
# .env から SESSION_SECRET_PREVIOUS の行を消す
docker compose -f docker-compose.prod.yml up -d app
```

**消し忘れないこと。** 残したままだと、**旧鍵はいつまでも有効**です——
入れ替えた意味がなくなります。

> **カレンダーに 7 日後の予定を入れてから始めてください。**
> 手順 4 は「あとでやる」が最も忘れられます。

## SECRET_MASTER_KEY（保存済みの秘密を暗号化している）

**これは上と違い、そのままでは替えられません。**
DB に保存済みの値がこの鍵で暗号化されているため、
替えると**読めなくなります**（＝失われます）。

替える必要があるときは、**復号 → 新しい鍵で再暗号化**の移行が要ります。

1. バックアップを取る（[BACKUP_RESTORE.md](BACKUP_RESTORE.md)）
2. 旧鍵で全件を復号し、新しい鍵で保存し直すスクリプトを書く
3. **検証環境で先に通す**（[ENVIRONMENTS.md](ENVIRONMENTS.md)）
4. 本番で流す。**流している間は書き込みを止める**

**まだ移行スクリプトはありません。** 必要になった時点で
`scripts/` に置き、この節から参照してください。

## 外部 SaaS の鍵（Zoho / Stripe / Twilio など）

**先に新しい鍵を作ってから、古い鍵を無効化してください。**
順番を逆にすると、その間ずっと連携が止まります。

1. SaaS の管理画面で**新しい鍵を発行**（古いものはまだ消さない）
2. `.env` を書き換えて再起動
3. **動くことを確かめる**（Zoho なら顧客情報が出るか）
4. SaaS の管理画面で**古い鍵を無効化**

**4 を忘れないこと。** 漏れた鍵が有効なままです。

## POSTGRES_PASSWORD

**DB 側とアプリ側の両方**を替える必要があります。片方だけだとつながりません。

```bash
# 1. DB 側で変更
docker compose -f docker-compose.prod.yml exec db \
  psql -U app -c "ALTER USER app WITH PASSWORD '<新しい値>';"

# 2. .env の POSTGRES_PASSWORD と DATABASE_URL を書き換える
# 3. アプリを再起動
docker compose -f docker-compose.prod.yml up -d app
```

**`DATABASE_URL` にもパスワードが入っています。** 片方だけ直すと落ちます。

## いつ替えるか

| きっかけ | 対象 |
|---|---|
| **漏れた・漏れた疑いがある** | 該当するもの**すぐ**（移行期間を置かない） |
| **担当者が退職した** | その人が見られたもの全部 |
| 定期的に | 年 1 回程度。**やらないより、緩くても続ける方がよい** |

**定期入れ替えを毎月にしないでください。** 続かなくなって、
結局「一度もやっていない」状態になります。
