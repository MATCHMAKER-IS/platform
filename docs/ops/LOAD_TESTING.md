# 負荷を測る（100 人規模に向けて）

**「今は速い」は「100 人でも速い」ではありません。**

このアプリは**数人で使っている間は何をしても速い**です。
100 人が毎日使うと、**1 年で経費 3 万件・監査ログ数十万件**になります——
**そのとき初めて遅くなり、そのときには直しにくくなっています**。

**先に測ってください。** 遅くなってから直すのは、
**動いているものを触ることになり危険**です。

---

## いつ測るか

| 場面 | なぜ |
|---|---|
| **いま（1 回目）** | 基準を取る。**これが無いと「遅くなった」が分かりません** |
| **利用者が 30 人を超えたとき** | 半分まで来た時点で傾向が見える |
| **一覧の画面を足したとき** | **新しい一覧が一番危ない**（索引を忘れがち） |
| **本番へ出す前** | 手元で速くても、本番の DB では違います |

## 測り方

```bash
# 1) DB とアプリを起動
docker compose up -d
pnpm dev:internal-app

# 2) 別の端末で測る
pnpm loadtest
```

**まず「いまの数」を記録してください。**
`ops/loadtest-baseline.json` に残しておくと、次回と比べられます。

## 何を見るか

### 平均ではなく p95 を見てください

**平均は外れ値に弱く、遅い人の体験が見えません。**

100 人のうち 95 人が 100ms、5 人が 10 秒なら——
**平均は 595ms** で「まあ速い」に見えますが、
**その 5 人は毎回 10 秒待っています**。

| 指標 | 意味 | 目安 |
|---|---|---|
| **p50** | 半分の人がこれより速い | **300ms 以下** |
| **p95** | 20 人に 1 人がこれより遅い | **1 秒以下** |
| **p99** | 100 人に 1 人がこれより遅い | **3 秒以下** |

**p99 は 100 人なら「毎日 1 人」**です。無視できません。

### 落ちた数を必ず見てください

**速くても落ちていたら意味がありません。**
`statusCounts` に 500 が混ざっていないか確認してください——
**負荷をかけて初めて出る不具合**があります。

## 遅かったときに見るところ

**上から順に見てください。** 下ほど直すのが大変です。

### 1. 索引（インデックス）が無い

**一番多い原因で、一番簡単に直ります。**

```sql
-- 遅いクエリを探す
EXPLAIN ANALYZE SELECT * FROM "Expense" WHERE "status" = 'pending' ORDER BY "createdAt" DESC;
```

**`Seq Scan`（全件走査）が出たら索引が足りません。**
`schema.prisma` に `@@index([status, createdAt])` を足してください。

**絞り込む列と並べる列を「組で」** 索引にしてください——
別々に作っても、**組み合わせでは効きません**。

### 2. 全件を読み込んでいる

**`take` が無い一覧**を探してください。

```ts
// 危ない: 3 万件を全部読む
const rows = await db.expense.findMany({ where: { status } });

// 直す: 必要な分だけ
const rows = await db.expense.findMany({ where: { status }, take: 50, skip });
```

**基盤の検査（`check-order-by`）が並び順は見ています**が、
**件数の上限は見ていません**——自分で確かめてください。

### 3. N+1（1 件ずつ引いている）

**一覧を出したあと、1 行ごとに関連を引く**形です。
50 件の一覧で **51 回のクエリ**が飛びます。

```ts
// 危ない: 申請ごとに申請者を引く
for (const e of expenses) e.user = await db.user.findUnique({ where: { id: e.userId } });

// 直す: まとめて引く
const rows = await db.expense.findMany({ include: { user: true } });
```

### 4. メモリ実装のまま

**`HANDOVER.md` の「100 人規模になると壊れるところ」**を見てください。
セッション・ロック・冪等キーがメモリのままだと、
**2 台目を立てた瞬間に壊れます**——これは遅さではなく**壊れ方**の問題です。

## 測ったら記録してください

**数字だけ残しても意味がありません。** 次の 3 つを書いてください。

1. **いつ、どれだけのデータで測ったか**（「経費 5,000 件のとき」）
2. **どの画面が遅かったか**
3. **何をしたら速くなったか**（索引を足した、`take` を入れた）

**「なぜ速くなったか」が残っていないと、次に遅くなったときに同じ調査を繰り返します。**

記録先: `docs/ops/HANDOVER.md` の「気づいたこと」

## やらない方がよいこと

| やりがちなこと | なぜ避けるか |
|---|---|
| **測る前に最適化する** | **どこが遅いか分からないまま複雑にする**ことになります |
| **キャッシュで隠す** | 遅い原因は残ったまま。**古いデータが出る**問題が増えます |
| **サーバを増やす** | **メモリ実装のままだと壊れます**（先に移行が要ります） |
| **全部の指標を追う** | 見きれません。**p95 と落ちた数**だけで十分です |
