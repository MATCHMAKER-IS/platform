# メールが届かないとき / 届くようにする

**届いていないことに、こちらは気づけません。**

社内システムでも、承認依頼・パスワード再設定・請求書の送付はメールで飛びます。
迷惑メールフォルダへ入ると、こう見えます。

| 実際に起きていること | 現場からはこう見える |
|---|---|
| 承認依頼が届いていない | 「まだ承認されない」（申請者は待ち続ける） |
| パスワード再設定のメールが届かない | 「ログインできない」（情シスに問い合わせが来る） |
| 請求書が届かない | 「入金が遅れている」（督促してから発覚する） |

**どれもシステムの障害としては現れません。** だから原因にたどり着くのに時間がかかります。

## まず確認する

```bash
node tools/check-mail-dns.mjs            # .env の MAIL_FROM から自動判定
node tools/check-mail-dns.mjs example.co.jp
```

## 3 つの設定

| | 何をするもの | 無いとどうなるか |
|---|---|---|
| **SPF** | この差出人ドメインは、どのサーバから送ってよいかを宣言する | 受け側が「なりすまし」と判断しうる |
| **DKIM** | 送信サーバが電子署名を付け、改ざんが無いことを示す | **転送されると SPF は失敗する**。DKIM はそれでも通る |
| **DMARC** | 失敗したときの扱いを宣言し、**レポートを受け取る** | **失敗していることに気づけない** |

### DMARC がいちばん見落とされます

SPF と DKIM は「設定した」で終わりがちですが、
**合っているかを教えてくれるのは DMARC のレポートだけ**です。

**まず `p=none` で始めてください。**

```
_dmarc.example.co.jp  TXT  "v=DMARC1; p=none; rua=mailto:dmarc@example.co.jp"
```

`p=none` は「**失敗しても何もしないが、報告はして**」という意味です。
いきなり `p=reject` にすると、**設定漏れがあった瞬間に自社のメールが全部止まります**。

数週間レポートを見て、**正当なメールが全部通ることを確かめてから**
`p=quarantine` → `p=reject` と上げてください。

### よくある落とし穴

| 症状 | 原因 |
|---|---|
| SPF はあるのに弾かれる | **`+all`** になっている（誰が送ってもよい＝何も守っていない） |
| SPF が「不明」扱いになる | **`include:` が 10 件を超えている**（上限。超えると設定が無いのと同じ） |
| 転送されると届かない | **DKIM が無い**。転送で送信元が変わり、SPF だけでは通らない |
| DMARC を設定したのに何も来ない | **`rua=` が無い**。レポートの宛先が指定されていない |

## 設定しても届かないとき

**DNS が正しくても、届くとは限りません。**

### 1. 実際に送って確かめる

主要な宛先へ送り、**受信箱に入るか**を見てください。

- Gmail
- Outlook / Microsoft 365
- **取引先のドメイン**（企業のフィルタは厳しいことがあります）

Gmail は受信したメールの「メッセージのソースを表示」で
`SPF: PASS` / `DKIM: PASS` / `DMARC: PASS` を確認できます。

### 2. 送信元 IP の評判

VPS から直接送っていると、**IP アドレスの評判**で弾かれることがあります。
共有 IP の VPS では、**過去にそのIPを使った誰かの行いが影響します**。

**送信サービス（SendGrid / Amazon SES / Google Workspace 等）経由にするのが確実です。**
自前の SMTP から直接送るのは、規模が小さくても割に合いません。

### 3. 内容で弾かれる

- 短すぎる本文＋リンクだけ
- 差出人の表示名と実アドレスが食い違う
- 添付が実行ファイル

## バウンス（届かなかった通知）をどう扱うか

**現状、バウンスは自動で処理していません。**

`@platform/mail` は送信の失敗（SMTP がエラーを返した）は再試行しますが、
**いったん受け付けられた後に「宛先が存在しない」と返ってくる**類は、
`MAIL_FROM` のメールボックスに届くだけで、誰も見ていません。

**当面の運用**として、次を決めておいてください。

1. `MAIL_FROM`（例 `no-reply@…`）を**捨てアドレスにしない**。受信できるようにする
2. **週に一度は見る**（担当を決める）
3. 宛先不明が続く相手は、`@platform/mail` の**送信先許可リスト**から外すか、
   利用者マスタのアドレスを直す

**放置すると評判が下がります。** 存在しない宛先へ送り続けると、
受信側から「雑な送信者」と見なされ、**正当なメールまで弾かれ始めます**。

将来的に自動化するなら、送信サービスの Webhook（バウンス通知）を
`/api/webhooks/…` で受けて、利用者マスタに印を付けるのが素直です。

## 検証環境から取引先へ送らない

**これが最も実害の大きい事故です。**

検証環境（`APP_ENV=staging`）では、SMTP を **Mailpit** に向けてください。

```
# .env.staging
SMTP_HOST=localhost
SMTP_PORT=1025
```

`@platform/mail` には**送信先の許可リスト**があります（`allowlist.ts`）。
本番以外では、自社ドメインだけを許可する設定にしておくと安全です。
