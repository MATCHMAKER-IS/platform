# 障害対応（本番が止まったら）

**あわてないでください。** この順にやれば大丈夫です。

> **今すぐやること**: http://本番URL/admin/ops を開く → 赤い項目を見る → 下の該当箇所へ

## 0. 最初の 5 分

```
① 運用ダッシュボードを開く      /admin/ops
② 何が壊れているか特定           赤い ❌ を見る

```


**原因が分からなくても連絡してください。** 「調査中」の一言があるかないかで、周囲の混乱が全く違います。

## 業務の異常を見る

システムのメトリクスが全部緑でも、**業務は止まっていることがあります**。

`POST /api/admin/business-metrics/scan` を **cron から 1 日 1 回**呼ぶと、
次がゲージに載ります（`system:manage` の権限が要ります）。

| メトリクス | 意味 |
|---|---|
| `business.overdue_invoices` | 期限を過ぎた未払いの請求書 |
| `business.overdue_tasks` | 期限を過ぎたタスク |
| `business.oldest_overdue_days` | **一番古い滞留の日数** |
| `business.pending_approvals` | 承認を待っている書類 |
| `business.oldest_pending_approval_days` | **一番古い承認待ちの日数** |
| `business.contract_alerts` | 更新期限・解約通知期限が近い契約 |
| `business.stale_assets` | **償却資産の申告で外し忘れている疑い** |

**`business.stale_assets` は年 1 回だけ見てください。** 固定資産税の申告前です
——**廃棄した資産を申告し続けると、払わなくてよい税を払い続けます**。
毎日見ても意味がなく、**申告の手順に組み込む**のが確実です。

**契約は放置すると自動更新されます。** `business.contract_alerts` は
**更新期限と解約通知期限の両方**を見ています——
**解約通知の期限を過ぎると、望まない 1 年が始まります**。

**件数より「日数」を見てください。** 10 件が 1 日遅れているのと、
1 件が 3 ヶ月放置されているのは、**件数では同じに見えて意味が違います**。

**アラートは設定していません。** 承認待ちは常に何件かあるのが正常で、
**閾値は運用が決めるもの**です——実際の数を 1 ヶ月ほど見てから、
`system-alerts` に条件を足してください。

## アラートを出すかの基準

**何でも鳴らすと、鳴っても見なくなります。** 次で分けています。

| 出す | 出さない（メトリクスだけ） |
|---|---|
| **滅多に起きない**——起きたら異常 | **日常的に起きる**——傾向を見るもの |
| 例: `outbox_exhausted`（通知が届いていない）、`cron_failed`（定期実行が止まった）、`audit_write_failed`（記録できていない） | 例: `upload.exif_present`（スマホの写真はほぼ全部 EXIF 付き）、`http_requests_total` |

**判断のしかた:** 「これが 1 件出たら誰かが動くか」を考えてください。
動かないなら**メトリクスに留める**べきです——
**鳴り続けるアラートは、本当に鳴るべきときにも無視されます**。

**メトリクスに載せておけば、増えたときに気づけます。**
`upload.exif_present` が急に増えたら、
「スマホからのアップロードが増えた」＝**変換の仕組みを入れる合図**です。

## アラート別の対応

`system-alerts` が鳴ったときの手引きです。**アラート名で引いてください。**

### `http_error_rate`（エラー率 1% 超）

1. **どの API か**を絞る——メトリクスの `http_errors_total` にパスのラベルがあります
2. **直前のデプロイを疑う**。心当たりがあれば戻す（`docs/ops/DEPLOY_AWS.md`）
3. 心当たりが無ければ「症状別の対応」へ

### `http_latency`（平均 500ms 超）

**平均で見ているので、これが鳴る時点でかなり遅い状態です**
（目標は p95 300ms。測り方が追いついていない——ADR 0012 の現況を参照）。

1. **DB を疑う**——遅いクエリが無いか（`pnpm db:psql` で `pg_stat_statements`）
2. **外部連携を疑う**——`google` / `microsoft` / `freee` は 10 秒で切れますが、
   **10 秒待つこと自体が遅い**

### `outbox_exhausted`（通知の再試行が上限）

**届いていない通知があります。** 経費の承認依頼なら、
**申請者は「まだ承認されない」、承認者は「依頼が来ていない」と思ったまま止まります**。

1. **何が届いていないか**を確認——ログの `exhausted` の件数と種別
2. **送信先を疑う**——メールサーバ・Slack の障害が多い
3. **手で連絡する**——止まっている承認があれば、当事者に直接伝える
4. 復旧後、**Outbox に残っているものは自動で再送されません**（諦めた状態）
   ——必要なら手で作り直す

### `cron_failed`（定期実行の失敗）

**通知やレポートが止まっています。** 放置すると `outbox_exhausted` に進みます。

1. **どのジョブか**——メトリクスの `cron_runs_total{job=…}` を見る
2. **ロックを疑う**——**現在はメモリ実装なので、再起動でロックが消えます**
   （2 台構成なら両方が走ります。`docs/ops/HANDOVER.md` の移行手順を参照）
3. 手で 1 回実行して様子を見る

### `audit_write_failed`（監査ログの記録失敗）

**追跡できない操作があります。** 監査のときに
**「記録が無い＝していない」と誤読される**ので、**記録できなかった事実を残してください**。

1. **DB を疑う**——監査ログは DB に書きます。容量・接続を確認
2. **いつからいつまで**記録できていないかをメモに残す
3. 復旧後、**その期間の操作は追えない**ことを関係者に伝える

## 症状別の対応

### 画面が開かない（真っ白・エラー画面）

```bash
# 1. サーバは生きているか
curl https://本番URL/api/health
```

| 結果 | 意味 | 対応 |
|---|---|---|
| `{"ok":true}` | サーバは生きている | **画面側の問題**。ブラウザの Console を見る（[DevTools ガイド](DEVTOOLS_GUIDE.md)） |
| 応答なし・タイムアウト | サーバが落ちている | → 下の「サーバが落ちた」 |
| 502 / 503 | サーバは起動中か、落ちた直後 | 1 分待って再確認。それでもダメなら「サーバが落ちた」 |

### サーバが落ちた

```bash
# 1. プロセスは動いているか（デプロイ先で）
pm2 status              # ConoHa VPS の場合
# または
docker ps               # コンテナの場合

# 2. ログを見る（原因はほぼここに出ている）
pm2 logs --lines 100
# または
docker logs --tail 100 <コンテナ名>
```

**ログで探すもの**:

| ログの内容 | 原因 | 対応 |
|---|---|---|
| `環境変数の検証に失敗` | 設定漏れ | `.env` を確認。必須は `DATABASE_URL` / `SESSION_SECRET` / `MAIL_FROM` |
| `秘密値の強度が不十分` | 開発用の値のまま | 強いパスワードを生成して設定（[公開する](../onboarding/03-development.md#7-公開するデプロイ)） |
| `ECONNREFUSED` + ポート 5432 | DB に繋がらない | → 下の「DB に繋がらない」 |
| `JavaScript heap out of memory` | メモリ不足 | 再起動 → 根本対応は「メモリが足りない」へ |
| `EADDRINUSE` | ポートが使われている | 古いプロセスが残っている。`pm2 delete all` してから起動 |

```bash
# 3. とりあえず復旧させる
pm2 restart all
# または
docker compose restart
```

**再起動で直ったら、それで終わりにしないでください。** なぜ落ちたかをログから特定します（次に必ずまた落ちます）。

### DB に繋がらない

```bash
# 1. DB は生きているか
psql "$DATABASE_URL" -c "SELECT 1"
```

| 結果 | 対応 |
|---|---|
| `1` が返る | DB は生きている。アプリ側の設定（`DATABASE_URL`）を確認 |
| `Connection refused` | DB が落ちている。DB サービスを再起動 |
| `too many connections` | **接続が枯渇**。アプリを再起動すれば一旦回復。根本対応は接続プールの見直し |
| `password authentication failed` | 認証情報が違う。`DATABASE_URL` を確認 |

### 特定の機能だけ動かない

`/admin/ops` の該当項目を見ます。

| 項目が ❌ | 原因 | 対応 |
|---|---|---|
| **Zoho** | 外部 API の障害・認証切れ | サーキットブレーカーが開いています。**しばらく待つ**（自動で復旧を試みます）。長引くならトークンを確認 |
| **Webhook** | 配信先が落ちている | 相手側の問題。再送キューに溜まるので、復旧後に自動で流れます |
| **監査ログの整合性** | **改ざんの疑い** | **至急、責任者に報告**。`/admin/audit` で該当箇所を確認。触らずに保全 |

### メールが届かない

| 確認 | 方法 |
|---|---|
| 送信自体はできているか | ログに `mail sent` があるか |
| SMTP の設定 | `/admin/env` で `SMTP_HOST` / `MAIL_FROM` を確認 |
| 迷惑メール | 受信者の迷惑メールフォルダ |

> 開発環境では**実際には送信されず** Mailpit（http://localhost:8025）に届きます。本番と混同しないこと。

### 「遅い」と言われる

```bash
# 1. 実際に測る（体感は当てにならない）
pnpm loadtest -- --url https://本番URL/api/health --concurrency 5 --iterations 50
```

> **本番に負荷をかけすぎないでください。** 並列 5・50 回程度に留めます。

| 結果 | 対応 |
|---|---|
| p95 < 300ms | **遅くない**。特定の画面だけか確認（DevTools の Network で該当 API を見る） |
| p95 > 1000ms | 遅い。DB のクエリを疑う（N+1・インデックス漏れ） |
| エラーが混ざる | 遅さより先にエラーを潰す |

基準値: [ADR 0012](../adr/0012-performance-targets.md)

### 全員が使えない・原因不明

**メンテナンスモードにして、落ち着いて調べます。**

```
/admin/maintenance で ON
```

利用者には「メンテナンス中」の画面が出ます。中途半端に動いてデータが壊れるより安全です。

## 直し方が分からないとき

### ロールバック（前のバージョンに戻す）

**迷ったら戻す。** 原因究明は復旧してからで構いません。

> **「前回の成功したデプロイを Re-run」では戻りません。**
> それは同じ手順をもう一度実行するだけで、**取ってくるのは壊れた最新**です。
> 2026-08 まで、この資料にはその手順しか書いてありませんでした。

#### いちばん速い方法（1〜2 分）

**1. 戻す先のタグを調べる**

イメージには **コミットの sha が付いています**（`sha-abc1234`）。
GitHub の **Actions → Release → 前回成功した実行** を開くと、
`Build & push app` のログにタグが出ています。
または `git log --oneline -5` の**短い sha** がそのまま使えます。

**2. そのタグで出し直す**

Actions → **Deploy to ConoHa** → Run workflow →
`image_tag` に `sha-abc1234` を入れて実行。

サーバに入れるなら、こちらの方が速い:

```bash
cd ~/app
IMAGE_TAG=sha-abc1234 docker compose -f docker-compose.prod.yml pull
IMAGE_TAG=sha-abc1234 docker compose -f docker-compose.prod.yml up -d app
```

**`migrate` は流さないでください。** アプリだけ戻します（下記）。

#### スキーマはどうするか

**戻しません。** マイグレーションは前進のみです（ADR 0014）。

前の版のアプリは、**新しいスキーマの上でも動く**のが原則です——
そのために破壊的変更を 2 段階（列を足す → 移行 → 読み先を変える →
十分あとで消す）に分けています。

**この原則が守られていれば、アプリだけ戻せば復旧します。**
守られていない変更（列をいきなり消した等）をしてしまった場合は、
アプリを戻しても動きません。**バックアップからの復元**になります
（[BACKUP_RESTORE.md](BACKUP_RESTORE.md)）。

#### 戻したあと

```bash
git revert <壊れたコミット>   # 打ち消しコミットを作る
git push                     # 次のデプロイで正しい状態になる
```

**これを忘れると、次に誰かがデプロイした瞬間に壊れた版へ戻ります。**
`IMAGE_TAG` での切り戻しは**その場しのぎ**で、リポジトリは壊れたままです。

> **`git reset --hard` で歴史を消さないでください。** `revert`（打ち消し）を使います。何があったかの記録が残ります。

### DB のマイグレーションを戻す

**危険です。データが消えることがあります。** 必ずバックアップを取ってから。

```bash
# バックアップ（先にやる）
pg_dump "$DATABASE_URL" > backup-$(date +%Y%m%d-%H%M).sql

# 戻す
pnpm --filter internal-app exec prisma migrate resolve --rolled-back <マイグレーション名>
```

自信がなければ**やらないでください**。アプリを前のバージョンに戻すだけで済むことも多いです。

## 復旧したら

### 1. 関係者に連絡

```
【復旧】社内アプリの障害は 11:02 に復旧しました
原因: DB の接続数が上限に達していた
対応: アプリを再起動。恒久対策は別途検討します
```

### 2. 記録を残す（15 分でいい）

GitHub の Issue に書きます。**次に同じことが起きたとき、これが全てです。**

```markdown
## 何が起きたか
10:15〜11:02、経費申請が保存できなくなった。全員に影響。

## 原因
DB の接続数が上限（100）に達していた。月初の申請集中が引き金。

## どう直したか
アプリを再起動して接続を解放。

## 恒久対策
- [ ] 接続プールの上限を見直す
- [ ] 接続数のアラートを設定する

## 気づいたこと
/admin/ops を見れば 1 分で分かったが、最初 30 分ログを追っていた。
→ 障害時はまず /admin/ops、を周知する
```

### 3. 責めない

**人ではなく仕組みを直します。** 「誰がやったか」より「なぜ気づけなかったか」「どうすれば防げたか」です。

犯人探しをすると、次から誰も報告しなくなります。それが一番危険です。

```bash

```

**復元を試したことがないバックアップは、無いのと同じです。** 月に一度は試してください。

# 観測の 3 層

**`docs/ops/INCIDENT_RESPONSE.md` を統合したものです（2026-08）。**

3 層で本番の状態を把握する。

1. **構造化ログ** … `@platform/logger`(pino)。JSON + requestId。機微情報は既定でマスク。
   - 収集: ConoHa なら journald / ファイル → 任意のログ基盤、AWS なら CloudWatch Logs。
2. **エラー追跡** … Sentry(`@sentry/nextjs`)。`apps/internal-app/src/instrumentation.ts`
   で初期化。`SENTRY_DSN` 未設定時は no-op。例外の能動的な通知・スタックトレース集約に使う。
3. **ヘルスチェック** … `/api/health`(DB ping)。LB / オーケストレータの死活監視に使う。

> ログは「起きたことの記録」、エラー追跡は「即座に気づくための通知」。役割が違うので併用する。
